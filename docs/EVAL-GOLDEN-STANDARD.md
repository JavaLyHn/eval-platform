# 评测黄金准则（Golden Standard）

> **权威级别**：本文件是 eval-platform 所有评测相关决策的**最高准则**。
> **来源**：Anthropic 工程博客《Demystifying Evals for AI Agents》(发布 2026-01-09)。本文为其方法论的中文提炼与本平台落地口径。
> **生效规则**：本准则为**顶层通用方法论**;任何应用层专属标准与之冲突,一律以本准则为准。
> **状态**：2026-06-01 确立。demo / 原型阶段——准则是目标基线,落地分步推进。

---

## 0. 适用与优先级

- **本准则(通用方法论)> platform 应用层标准 > 任何旧口径。**
- platform 应用层(6 员工画像、红线一票否决、P0/P1/P2、多 judge≥85%、6 类失败归因、保下限/Layer 反推)继续有效,但**必须符合本准则**;不符处按本准则修订。
- 所有新评测功能 / 指标 / 流程,先回答:**符合本准则吗?**

## 1. 术语（统一语言）

| 术语 | 定义 |
|---|---|
| **Task(任务/题)** | 一个测试:明确的输入 + 成功判据。 |
| **Trial(试跑)** | 对一个 task 的一次尝试;因模型输出有方差,**需多次 trial**。 |
| **Grader(评分器)** | 给 agent 表现某方面打分的逻辑;一个 task 可多个 grader。 |
| **Assertion/Check(断言)** | grader 内的单个判定条件。 |
| **Transcript / Trace / Trajectory(轨迹)** | 完整记录:输出、工具调用、推理、中间结果、交互。 |
| **Outcome(结果)** | 最终环境状态(如数据库确认下单,而非只看"确认"文字)。 |
| **Evaluation harness(评测台)** | 端到端基建:下发指令/工具、并发跑 task、记录步骤、打分、聚合。 |
| **Agent harness / Scaffold** | 让模型"作为 agent 行动"的系统:输入处理、工具编排、返回结果。 |
| **Evaluation suite(评测集)** | 衡量特定能力/行为的一组 task。 |

> **关键**:"评一个 agent" = **评 harness 和 model 一起**,不是只评模型。

## 2. 评分器三类 + 打分机制

- **代码型(code-based)**:字符串/正则/模糊匹配、二元 fail-to-pass/pass-to-pass、静态分析(lint/type/security)、**结果核验**、**工具调用核验(用了哪些工具、参数对不对——但不查死板顺序)**、轨迹分析(轮数/token)。→ 快、便宜、客观、可复现;但对合理变体脆、缺细腻度。
- **模型型(model-based)**:rubric 打分、自然语言断言、成对比较、参照答案对照、多 judge 共识。→ 灵活、可规模化、抓细腻度;但非确定、贵、**必须用人类专家校准**。
- **人工型(human)**:SME 评审、众包、抽审、A/B、标注者间一致性。→ 金标准;但贵、慢、需专家。
- **打分组合**:加权(综合分过线)/ 二元(全过)/ 混合。
- **选择原则**:**能用确定性(代码型)就用;需要灵活/细腻才上模型型;人工型审慎用于校准与主观判定。**

## 3. 能力评测 vs 回归评测

- **能力评测**:"这 agent 能做好什么?"——起点低通过率,瞄准它做不好的,提供"往上爬的坡"。
- **回归评测**:"以前会的现在还会吗?"——目标≈100%,掉了 = 退化,要查。
- **演化**:能力题刷到高通过率后**毕业**成回归题。

## 4. 非确定性：pass@k / pass^k（本平台重点）

- agent 每次跑结果会变 → **单次 trial 不可信,必须多 trial**。
- **pass@k**:k 次里**至少 1 次**对的概率(随 k 升)。适合"提多个方案,有一个能用就行"。编码常看 pass@1。
- **pass^k**:k 次**全部**对的概率(随 k 降)。适合**面向客户、要求每次都可靠**的场景。
- **本平台裁定**:**面向客户的员工(含 Aria/Sam)、以及"保下限"判定,用 `pass^k`**——下限是"每次都不能破",不是"偶尔一次过"。

## 5. 按 agent 类型的评测策略

- **编码 agent**:良定义 task + 稳定环境 + 充分测试。主用确定性 pass/fail,次用轨迹/LLM rubric 评代码质量。
- **对话 agent(Aria/Sam 属此类)**:不仅评结果,**还评"交互质量本身"**。做法:可核验的终态(state check)+ rubric(任务完成 + 交互质量)+ 常需**第二个 LLM 扮演用户**多轮模拟;多维成功(解决了 + 轮数约束 + 语气得体)。
- **研究 agent**:专家对"全面/可靠来源/正确"会分歧。组合打分:**groundedness(有据)+ coverage(必含要点)+ 来源质量 + 客观题 exact match + LLM rubric**;rubric **频繁对齐人类专家**。
- **计算机操作 agent**:真/沙箱环境跑,查真实结果(如订单真下了,而非只出现确认页);DOM(快/费 token)vs 截图(慢/省 token)按场景选。

## 6. 八步路线（Zero → Reliable Evals）

0. **尽早起步**:别等"完美题库",**20–50 道真实失败题**就能开干;拖越久越难建。
1. **把人工测试转成 task**:从开发时已在跑的检查、bug 追踪、客服队列里取,按用户影响排序。
2. **写无歧义 task + 参考解**:**两个领域专家独立判定结果一致**才算无歧义;task 必须"按指令正确做就能过";前沿模型 0% pass@100 通常是题坏了,不是 agent 不行。
3. **建平衡题集**:**正反都测**(该做的场景 + 不该做的场景),否则单边优化(只测"该搜索"→ 啥都搜)。
4. **稳健 harness + 隔离环境**:eval 里 agent ≈ 生产里;**每个 trial 从干净态起**,禁止共享状态(残留文件/缓存)造成相关性失败或虚高。
5. **谨慎设计 grader**:**评产出/结果,不评路径**;别查死板的工具调用顺序;多组件任务给**部分分(连续光谱)**;模型 judge 要**人类校准 + 给"Unknown"出口防幻觉 + 每维度独立 judge + 防作弊绕过**。
6. **读轨迹(不可省)**:不读大量 trial 轨迹,就不知道 grader 灵不灵;失败时分清"真错"还是"有效解被误杀"。
7. **盯饱和**:接近 100% 时大能力提升只显示为小分数变化;别只看分,要有人挖细节、读轨迹、验公平。
8. **当活文档维护**:像维护单测一样;推 **Eval-Driven Development**(先写能力 eval 再让 agent 满足);**让最懂产品/用户的人(PM/CSM/销售)经 Claude Code 贡献题**。

## 7. DO / DON'T

**DO**:确定性优先、正反都测、无歧义题+参考解、评结果不评路径、多组件给部分分、trial 间环境隔离、LLM judge 对齐人类、**常读轨迹**、早验可解性、建平衡集、持续跑回归、跟踪基线(延迟/token/成本/错误率)、广纳贡献、研究类多 grader 组合、按需选 pass@k / pass^k。

**DON'T**:别等完美才动手、别查死板工具调用顺序、别罚有效变体、别只测正例、别不读轨迹、别只信分数不读样本、别用歧义题、别让 trial 共享状态、别一刀切不给部分分、别用含糊 rubric、别拖到上量才做、别用误导性判分罚"听话"的模型、别把 eval 当死物、别只靠单一评测方法。

## 8. 瑞士奶酪：多方法兜底

没有单层能抓住所有问题。**自动评测(快速迭代)+ 生产监控(真实地面真值)+ 人工抽审(校准)+ A/B(真实结果)** 叠起来,一层漏的另一层接。最有效的团队四者并用。

## 9. 与 platform 应用层标准的衔接 + 三处冲突裁定

platform 应用层标准整体保留,但以下**冲突处一律以本准则为准**,平台与设计据此修订:

| # | 冲突点 | 旧做法(platform/平台) | **裁定(以本准则)** |
|---|---|---|---|
| 1 | **多 trial / pass^k** | 基本单次评测(多 judge 校准 ≠ 多 trial) | **同一 task 多次 trial**;面向客户 + 保下限用 **pass^k**;单次结果不作准 |
| 2 | **部分给分** | 偏 strict Pass/Fail 双向 | 多组件任务**给部分分/连续光谱**(保下限的红线项仍可保持硬判) |
| 3 | **评结果不评路径** | 6 类归因/探针含按工具·参数判 | **以结果/产出为主**;工具调用只查**关键项是否发生**,**不查顺序**;归因用于诊断、不作硬判死板路径 |

> 说明:多 judge≥85% 一致(platform)与本准则"模型 judge 需人类校准 + 每维度独立 judge"**兼容**,继续保留并加上"每维度独立 judge"。

## 10. 对本平台 / 保下限设计的影响（据此修订）

- **保下限**:探针题改为**多 trial 跑 + pass^k**("每次都守住"才算在位);要素核对**评结果/行为**,工具/参数只查关键项不查顺序;红线项保持硬判,其余可给部分分。
- **AI 出题 / 探针**:每题带"该不该触发"的**正反样本**;题要无歧义、可解、配参考解。
- **评委**:每维度**独立 judge** + 给"Unknown"出口 + 人类校准;接 L0–L5 评委升级(轨迹级核对是 §1 "读轨迹"的自动化形态)。
- **报告**:展示 pass@k / pass^k、基线(延迟/token/成本/错误率);"达标"判定基于 pass^k 而非单次。
- **流程**:能力评测与回归评测分开;评测集当活文档维护。
